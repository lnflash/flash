# Redis and identity/bank failure telemetry

This follow-up is based on `b76ed0ec1` and requires the central telemetry patch `4921212ac`. No production configuration, credentials, Redis connection, provider call or span export was accessed during implementation.

The installed IORedis plugin defaults to recording command-dependent arguments in `db.statement`. The application's Plaid binding store uses `plaid:link:${linkToken}` as a real Redis key, so SET/GET/DEL spans could expose a live bank-link capability despite the generic wrapper fix. IORedis instrumentation now uses a serializer that returns only the command name. It does not change Redis commands, keys, values, Lua, authentication, response callbacks or the one-use Plaid store. Tests execute the exact installed plugin's command wrapper with SET/GET/DEL/EVAL/AUTH fixtures, supplying a fake parent span because the production plugin requires one. Original command arguments, return values and completion callbacks remain intact while their contents are absent from attributes. Existing Plaid ownership/atomic-consumption/concurrency tests continue to pass.

ERP identity and bank failures previously passed raw Axios errors into the logger. Axios retains request configuration, including the ERP API Authorization header and submitted identity/bank body; pino's error serializer copies those enumerable properties. The current request-header redaction paths do not cover `err.config`. Some bank-request failures additionally logged `req.toErpnext()` directly. The span recorder also copied provider exceptions/messages, and returned domain-error messages could retain provider text for later tracing.

Upgrade requests, identity verification/status, bank reads/writes/change requests and their shared status updates now use one safe failure recorder. It accepts only closed operation names, an allowlist of known transport codes, and an integer HTTP status in 100–599. Logs and spans receive a fixed failure message and that bounded metadata; no raw error object/message/stack, request context, provider response, bank-number suffix or provider exception is retained. The identity-create warning level remains a warning. Generic returned errors retain their domain classes with fixed text so later wrappers cannot collect the original payload through the error message.

Bank refusal classification still examines the provider response locally and preserves the existing duplicate/not-owned/upgrade-required classes and allowlisted validation messages. It discards provider prose after classification. Unsuccessful 2xx bank replies and bulk-update failed-document payloads likewise produce the same generic error classes without retaining provider text. Provider HTTP calls, authentication headers, request bodies and successful results are unchanged; a missing decision-reason record still returns null on HTTP 404.

Validation: 213 tests pass across seven focused/existing suites, including all 21 affected ERP request/status entry points, original bank refusal mappings, ID/status behavior, and Plaid ownership/single-use behavior. Fake credential/body/message/stack/response fixtures are checked against serialized log, span and returned-error output; provider body/header assertions verify the required private data still reaches the mocked intended provider. Three TypeScript configurations, scoped ESLint and `git diff --check` pass using Node 24 and frozen-lock dependencies; no private `.env` file is loaded.

This is not a global telemetry guarantee. Other ERP cashout/settings/referral/Bridge-ledger paths still log raw Axios errors/provider responses in the baseline and require the same separate audit before claiming all ERP credential failures are safe. GraphQL coercion/parser/validation errors, other explicit trace attributes, generic exception handling, inbound/outbound HTTP URLs, direct logger calls and historical collector data remain separate sinks. Mongo instrumentation currently has enhanced value reporting disabled; this patch does not change its serializer or claim all database metadata is anonymous. Dev collector redactions are defense in depth only and do not establish the production collector policy or historical deletion/credential rotation.
