# Owned Bridge verification links

This change hardens the existing `bridgeInitiateKyc` mutation without changing GraphQL fields or input types. It is based on `7402dd7fcf49e378e4af5189232dffb76a4564d5`. It has not been deployed and no provider request or production mutation was made during implementation.

For an account with a stored `bridgeCustomerId`, the service retrieves links through the provider's current existing-customer endpoints:

- `GET /customers/{customerID}/kyc_link`
- `GET /customers/{customerID}/tos_acceptance_link`

The customer ID comes only from the fresh authenticated account record. Caller email, name and requested KYC type cannot select another customer. The service rechecks the stored association before exposing the response. Existing status is retained: in particular, `under_review`, `incomplete`, `awaiting_questionnaire` and `awaiting_ubo` are never reset to `open` or `not_started`. A provider GET failure is returned without a fallback customer-creation POST.

These endpoints and response shapes are documented by [Bridge's existing-customer KYC endpoint](https://apidocs.bridge.xyz/api-reference/customers/retrieve-a-hosted-kyc-link-for-an-existing-customer) and [existing-customer terms endpoint](https://apidocs.bridge.xyz/api-reference/customers/retrieve-a-hosted-url-for-tos-acceptance-for-an-existing-customer). The identity host is exactly `bridge.withpersona.com`; terms accept exactly `dashboard.bridge.xyz` or `compliance.bridge.xyz`, reflecting Bridge's documented hosted URLs. HTTPS, bounded printable URLs and no credentials, port, fragment, encoded host or host suffix tricks are required. Returned capabilities are not logged. Provider error responses containing someone else's `existing_kyc_link` are discarded before the error leaves the service.

For an account without a customer association, an explicit initiation can create a customer. Account-level locking serializes fresh reads, provider creation and local binding. A stable per-account UUID is supplied as the provider idempotency key; changing caller email or name cannot select a new key. The verified identity repository email remains preferred over caller input, preserving the existing input contract. The repository binds the returned customer using a compare-and-set predicate that matches only a missing/null `bridgeCustomerId`; it cannot overwrite an association established concurrently by another writer or older server. A final account read checks that the association still matches before links are returned.

Duplicate-email errors do not bind the returned existing customer, return its links, or reset verification status. Such failures need an explicit account/status review or support reconciliation. There is no automatic retry. The stable UUID is useful within the provider's idempotency retention; it does not promise unlimited exactly-once behavior after provider retention expires or eliminate an orphan customer if the provider succeeds but local persistence fails.

The [Bridge status lifecycle](https://apidocs.bridge.xyz/platform/customers/customers/kyclinks) distinguishes incomplete/action-required customers from manual review, and notes that some `under_review` customers still need identity information. Returning the current customer's hosted links supports continuation without creating another customer; no redirect, page text, app return or returned URL proves approval. `bridgeKycStatus` remains the source of server status and may proactively provision a receiving account after approval in this baseline.

Native clients must not assume this behavior exists until this backend change is released. The current native UI offers retained-link continuation only and otherwise directs users to refresh/support; a null or unknown status is not presented as new-customer eligibility. The real `bridgeTopupEnabled` rollout setting remains the product gate. No new deployment-attestation switch is introduced. A client adopting the current provider terms endpoint must explicitly review the documented `compliance.bridge.xyz` origin in its own initial-URL policy; it must not broaden to arbitrary Bridge subdomains.

Validation uses Node 24 and mocked provider/repository boundaries. Focused tests cover owned GET routing, preserved statuses, no caller-email rebinding, malformed/error responses, expiry of lock authority, fresh owner-association checks, stable-key retries, concurrent starts, atomic local binding and the unchanged public resolver. No secrets or real `.env` files are needed. A real provider sandbox and real Mongo/Redis integration run remain separate release checks.

Validation is performed with Node 24 and the fresh frozen-lockfile dependency installation from the combined review worktree, not the reused original installation. The prior two Express/Application type errors reproduced only with that reused installation; they are not a source/lockfile baseline failure. Current focused and compile results are recorded below. No casts or type workarounds were added. Five broader suites need environment bootstrap; a future combined run can use an explicitly constructed nonsecret regtest environment with loopback-only hosts, without reading `.env` or inheriting provider credentials.

The authenticated Bridge request adapter now rejects every redirect centrally (`redirect: "error"`), covering both hosted-link GETs, KYC creation, and existing GET/POST/DELETE operations. It does not follow even same-origin redirects. Custom `Api-Key` headers and financial/identity request bodies must never be forwarded to a redirect target. Real loopback-server regressions with dummy keys verify that the two new GETs, KYC POST and representative existing GET/POST requests never reach the redirect destination. No provider or production request is involved.

Stored and newly returned customer IDs pass a shared bounded ASCII letters/digits/underscore/hyphen validator before dispatch or local binding. Dot segments, encoded paths, URL delimiters, Unicode and control characters are rejected. Encoding alone is insufficient because `encodeURIComponent("..")` leaves a URL-normalized dot segment.

Historical ownership is checked without a unique index or migration. The repository returns at most two IDs, projecting only `_id`, for an exact customer-ID match. Existing-link retrieval requires exactly the current account before the GETs and again before reveal. A new binding requires zero current owners and exactly the new owner afterward. New paths always acquire locks in account → `locks:bridge-kyc-customer:<id>` order, holding the customer lock across ownership checks and binding/reveal. Both lock signals are checked again after the final owner-query await, and before CAS after the no-owner query. Callback provider errors are sanitized inside the customer-lock callback before the real lock adapter can convert a thrown callback exception; only safe API class/status survive, never provider bodies or arbitrary exception fields.

The baseline schema does not uniquely index `bridgeCustomerId`, and the prior duplicate-email fallback may already have created shared or incorrect associations. Shared rows now fail closed; the service never chooses the first match or repairs ownership by email. A solitary historical association can still be wrong, and older writers bypass the new customer lock. These guards are not a global database uniqueness guarantee and do not replace an authenticated historical-data audit before rollout. No automatic reassignment, migration, cleanup or unique-index creation is performed.

Final isolated validation with the fresh exact lockfile dependencies: 81 focused tests passed across four suites, including real loopback redirect regressions with dummy credentials; the 14 independently runnable Bridge-related suites passed 233 tests. Touched-file ESLint, `git diff --check`, declaration typecheck (`tsconfig.d.json`), whole-tree `tsc --noEmit`, and production configuration typecheck (`tsconfig-build.json`) all passed with zero diagnostics. An independent reviewer reran all 81 focused tests and found no remaining scoped KYC blocker. These checks still do not substitute for provider sandbox and real Mongo/Redis release validation.

Release dependency: the generic telemetry wrappers in this source baseline capture arbitrary function arguments, including KYC name/email and other application credentials. This isolated patch sanitizes provider error payloads and its direct service logs; it does **not** fix that central user-input tracing behavior. The separately reviewed central telemetry security patch must be integrated before this KYC change is considered for release. There is no method-specific tracing bypass in this patch and no claim that its user-input tracing is sanitized on its own.
