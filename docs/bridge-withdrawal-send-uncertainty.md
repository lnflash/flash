# Bridge withdrawal send uncertainty

This leaf starts from integrated backend `0ab8c6240`. It addresses the debit ambiguity between IBEX crypto send and Bridge payout; it does not change provider adapters, amount conversion, withdrawal-fee consent or enable native withdrawal initiation. No real provider request, payment, credential, exported span or deployment was used.

Previously any `sendCrypto` error made the withdrawal `send_failed`. The reconciler automatically deleted the Bridge transfer for that state. A timeout after IBEX accepted a debit could therefore cancel the destination while funds were already moving. A process crash or failed receipt write could also leave a submitted row without evidence that the send had begun.

Before calling `sendCrypto`, the service now reserves the exact submitted row using an atomic owner/transfer/state CAS. The write requires majority acknowledgment and journaling. It stores a new attempt UUID, attempt time, source wallet, send-info ID and original major-unit amount, and sets `send_unknown`/`attempted`. There is no transition back to an eligible request on errors. An index on `accountId`, unique only for `send_unknown`, prevents concurrent distinct rows from dispatching for the same account. The repository creates/verifies that exact named index using majority commit quorum before it grants dispatch authority; index, read, CAS or write-concern errors fail closed before provider dispatch.

Thrown or returned send errors, malformed acknowledgments, missing IDs, and receipt-persistence failures retain the fence. A usable IBEX ID can be stored against that exact attempt, but the state stays `send_unknown`. The pinned `ibex-client` `CryptoSendResponse200` has optional IDs and free-form optional status fields; it does not establish that `PENDING` means the funds were sent or settled. No positive status allowlist or local balance adjustment is invented. The service returns the closed `BRIDGE_WITHDRAWAL_SEND_OUTCOME_UNKNOWN` error with fixed instructions to check status and avoid submitting again; it does not return an error-free initiation result that RN would interpret as final success. No `usdt_sent` notification or ERP event is created from an uncertain acknowledgment. The existing completed-ERP writer can upsert from the later authoritative Bridge webhook.

Only the exact Bridge transfer's authenticated `payment_processed` read or explicit signed webhook state can clear the new uncertainty as completed. Repository completion of `send_unknown` or legacy `send_failed` requires a closed internal proof argument. An event name such as `transfer.completed` alone cannot clear it. The webhook acknowledges a typed unresolved-state refusal as HTTP 200 `pending_review`, performs no completed audit/notification, and leaves authenticated reconciliation to establish the state. Database faults retain HTTP 500. Existing known submitted/usdt-sent behavior remains compatible. Failed/returned/cancelled Bridge states never establish that an IBEX debit did not occur and cannot clear the new fence or authorize an automatic refund/resend.

Definitive errors before the crypto-send call remain distinguishable. Requirements/send-info failures set `send_failed` with explicit `cryptoSendState: not_dispatched` and fixed failure text. The repository cannot write this proof over an attempt fence. Automatic Bridge cancellation is permitted only for that proof with no attempt ID. Historical `send_failed` records have no such proof and are quarantined; they are not presumed safe to cancel. Account-level reads also block new requests/attempts for historical submitted rows, ambiguous send failures and sent rows missing a payout ID. This blocks a retry using a newly created row as well as reuse of the original row.

The scanner includes cross-age unresolved rows rather than dropping them after fifteen minutes. Each run reads at most 100 records with a five-second Mongo query budget. The `(status, cryptoSendReviewedAt, _id)` index supports the active-state scan. Separate review timestamps rotate the queue fairly without changing financial status or the original update/attempt times. Submitted rows receive the existing fifteen-minute grace before review. Review-bookkeeping faults are reported with fixed diagnostics; they never authorize cancellation or dispatch. Provider lookup errors or mismatched transfer IDs preserve uncertainty. The scan performs at most one lookup/cancellation per selected row and does not automatically retry a money send.

New uncertainty logs and operator alerts contain a closed reason and `SHA256("bridge-send:" + withdrawalRecordId)` reference. They exclude account/wallet IDs, addresses, amounts, provider errors/responses and credentials. The alert is best-effort; the Mongo fence is the durable authority. Existing unrelated Bridge logging, operational alerts and historical telemetry are outside this privacy claim.

## Release and recovery

Before any IBEX debit, the Bridge create-transfer response must also match the
reviewed customer, Ethereum/USDT source, ACH/USD destination external account,
and Ethereum/USDT deposit instructions. The returned transfer ID must be a
single safe identifier and its deposit address a 20-byte hex address. Missing
or mismatched receipt fields now refuse dispatch and leave the Bridge transfer
for operator review; no inferred destination or automatic retry is permitted.
Verify these returned fields with a sandbox transfer before enabling the
withdrawal flow. The response amount is not treated as a USDT debit quote;
immutable fee/source/expiry consent remains a separate release gate.

Quiesce all old withdrawal writers and reconcilers before activation; old processes do not honor the new fence/proof marker. Build and verify the named unique partial index and the review-queue index before accepting traffic. MongoDB must support majority index commit quorum (4.4+ replica set), and the application must be able to verify/create the index and perform majority journaled writes. Unsupported topology, permissions, duplicate existing unknown rows, conflicting index options or unknown acknowledgments block dispatch rather than falling back to weaker writes. Runtime creation verifies the required uniqueness; no index or historical record was changed during this development work.

Operators should list protected unresolved records, derive the alert reference from the record ID, and correlate the immutable source/send-info/attempt and any receipt ID with authoritative IBEX debit records and the owned Bridge transfer. A missing lookup result, timeout, pending response or absence of a webhook is not proof of no debit. Confirmed Bridge `payment_processed` can complete through the guarded repository path. Other outcomes require reviewed provider evidence and a separately authorized repair; this leaf adds no force-reset, blind retry, cancellation or refund endpoint. Never reset a fenced record to pending to unblock an account. Historical submitted/failed rows and a concurrent losing row may remain conservatively blocked for operator review. Ambiguity is deliberately retained when safe recovery cannot be established.

GraphQL's withdrawal `status` remains a string, so `send_unknown` needs no schema change. Native commit `53b7de3` explicitly decodes it and shows “Transfer pending review” and “Do not start another withdrawal”, never failed or settled. Pinned RN confirmation shows the actionable mutation error and stays on screen; backend guards reject subsequent attempts even though RN has no dedicated pending-review screen. Native initiation remains unavailable independently of this backend fix.

Validation covers thrown/returned provider outcomes, missing/failure acknowledgments, persistence uncertainty, journaled CAS ordering, index failures/results, concurrent distinct-row account fences, new-row retry blocking, historical quarantine, bounded/fair reconciliation, exact-ID completion, and event-name-only webhook refusal. These are guarded mocked tests; the real Mongo index/replica-set behavior and provider integration require the normal pre-release integration lane. No live provider calls are part of validation.

Validation result: **255 tests across 12 reviewed suites** pass under Node 24 with fake `safeEnvironment`, the integration network guard and Watchman disabled. All three TypeScript configurations, scoped ESLint, Typos and `git diff --check` pass. The test suites cover actual repository CAS/index options and modeled Mongo uniqueness; they do not substitute for the deployment gate’s real replica-set index verification.
