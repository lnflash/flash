# GraphQL error trace privacy

This follow-up is based on `1a8ae3cce`, after the central argument/source and IBEX/Redis/identity-banking telemetry fixes. It makes no provider request, deployment, authentication policy or application error-response change.

`allowValues: false` and removing `graphql.source` are insufficient to protect failed requests. Standard GraphQL input coercion quotes supplied input in an error message when a required sibling is missing. In the actual public schema, `UserTotpRegistrationValidateInput` includes `authToken`, `totpCode` and `totpRegistrationId`; omitting a required field can cause the error to repeat the supplied bearer and OTP. The previous response hook serialized the full errors, original messages and paths into spans. The installed GraphQL instrumentation 0.35.2 also records parser and validation exception events outside that response hook.

The response hook now collects only a fixed failure kind, a total count aggregated across top-level and payload errors (capped at 128), and machine codes from a closed set of pinned public/Apollo codes, including the literal banking/Bridge helper mappings. The distinct-code list is capped at 16. Unknown codes become `UNKNOWN`; uppercase formatting alone does not make an arbitrary string safe. Mixed top-level/payload failures are identified as mixed. Root aliases, messages, original-error objects, stacks and JSON error payloads are not used as telemetry values or attribute names.

At the exporter boundary, spans are classified by the actual GraphQL instrumentation library name. Their attributes and events are projected onto validated operation type and fixed failure summaries. Caller-selected operation names, aliases/field paths, exception messages/stacks, arbitrary custom attributes/events and status descriptions are not retained. Span names become fixed parse/validation/execution/resolve phases. Timing and error status remain useful without exporting the request or its errors. This deliberate metadata policy also prevents a private value embedded in a syntactically valid operation/alias name from bypassing message removal. Generic non-GraphQL application spans are outside this projection; raw GraphQL source remains removed globally as before.

Tests exercise the exact installed plugin's execute path against the repository's real public SDL, with a malformed TOTP registration input containing public fixture bearer/OTP values. The original GraphQL errors still reach the caller unchanged, while the serialized exporter stand-in contains none of those values or private operation/alias names. Actual parser and validator error paths, original-error identity, private bank/name values, unknown machine codes and status text are also checked. No SDK exporter or collector is contacted.

This does not sanitize generic application-wrapper exception messages, non-GraphQL events, arbitrary explicit attributes/baggage or unrelated logs. In particular, an Axios/plain-object error converted to JSON before reaching a generic wrapper can still embed request credentials in its message. HTTP URL/target instrumentation may retain sensitive query strings; identity document URLs generated without an HTTP request should not be described as automatically captured merely because that default exists. These remain separate source-boundary audits, as do historical telemetry access/retention and credential rotation. Dev collector rules do not establish production policy.

Validation: 40 tracing tests pass; the combined nine focused/regression suites pass 236 tests. All three TypeScript configurations, scoped ESLint and `git diff --check` pass under Node 24 with frozen-lock dependencies. A source comparison confirms every one of the 29 literal `BANK_ACCOUNT_*` / `BRIDGE_*` public helper codes is present in the closed set. Root independently reviewed the projection and requested the banking-code/count refinements covered by the final tests.
