# Registration and remaining ERP failure privacy

This leaf is based on `c01beb680`, after the central argument/GraphQL, IBEX and Redis/identity-banking telemetry fixes. Its backend source baseline remains `7402dd7fcf49e378e4af5189232dffb76a4564d5`; integration with newer provisioning/wallet changes requires their separate contract review. No deployment, provider request, real secret or exported span was used here.

The post-registration helper no longer serializes `registration.body` before validating the callback key. It records only the fixed expected schema and outcome. Invalid user/phone failures and downstream account errors use fixed exception summaries instead of raw identifiers, phone numbers or original provider/error messages. The original returned error/account objects and provider inputs remain unchanged.

The adjacent Kratos pre/post-registration application routes likewise stop logging request bodies, phone suffixes, caller-selected schemas or raw error objects. Their failure records contain a closed operation/outcome, the fixed expected schema and HTTP status only. Existing callback authorization, validation/refusal classes, 401/400/500 statuses, pre-registration Kratos message IDs and success responses are preserved. Unexpected rejected service work is contained inside a generic 500 boundary so it cannot fall through the generic tracing wrapper with a private exception. The post-persist 500 response no longer interpolates the private error detail; its failure status and fixed operation text remain. This is application-route logging; it is separate from the public/admin PinoHttp access-log work and does not assert those access loggers exposed Appcheck headers.

Every remaining raw Axios/provider-response failure recorder in `ErpNext.ts` now uses the same closed safe boundary as identity/bank methods. This covers cashout draft/submit, journal deletion, exchange rate/settings/referral reads, financial history, Bridge ledger upsert/completion/find and both uncredited-history entry points. Required provider authentication, request bodies, URLs and successful results are unchanged. A failed financial read remains an error, never a zero/default. The existing legacy completed-burn lower-bound rule still skips a missing final amount and returns its original result, but its informational log no longer includes the provider row identifier.

Domain error classes and refusal decisions are preserved. Duplicate ledger classification still reads the private provider response locally, recovers the single raced row and performs the original guarded update; the response is not logged or returned as an error message. Financial shape errors use fixed text instead of copying provider row identifiers into errors. A failure never becomes a completed/paid/refunded claim.

Validation: all 19 reviewed mocked suites pass, **428 tests**, under Node 24 with the integration runner's `safeEnvironment` and network guard. Real validator suites that initially failed unrelated environment bootstrap also pass in that guarded fake configuration; no private `.env` file is sourced. Watchman is disabled for the run so its unrelated Unix socket does not violate the I/O guard. Focused tests check unauthorized body non-inspection, callback refusal/throw privacy, required provider body/auth preservation, all affected ERP failure paths, duplicate-transfer recovery and financial fail-closed/lower-bound behavior. All three TypeScript configurations, scoped ESLint and `git diff --check` pass.

This is not a guarantee for unrelated explicit attributes, other Frappe/Bridge service logs, generic JSON-wrapped errors, HTTP URLs/access logging, historical spans or collector retention. Original registration domain errors deliberately retain their application identity and may still contain input text internally; the authorized route boundary does not serialize them. Source-boundary protection does not establish historical credential deletion or rotation.
