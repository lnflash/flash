# Automatic trace input capture

This isolated patch is based on backend `7402dd7fcf49e378e4af5189232dffb76a4564d5`. It does not change authentication, provider requests, payment execution, GraphQL results, or deployment configuration. It has not been deployed. Tests use fake spans and an in-process exporter stand-in; no span or credential is sent to a collector.

The generic synchronous and asynchronous wrappers previously copied the first argument into `code.function.params.*`. Object inputs exposed fields such as device passwords, OTPs, bank details and Bridge identity information. A positional string, including a session bearer, was enumerated as character indices. Null/undefined marker attributes did not make the values safe. Both wrappers now record only function name, namespace, root selection and explicitly supplied `spanAttributes`. They do not inspect, enumerate or read argument properties for tracing. Calls, arguments, results, returned/partial errors and thrown error identity retain their existing behavior. There is no argument-capture option or per-method opt-in.

Repository consumers of `code.function.params.*` are collector deletion rules in `dev/otel-agent-config.yaml` and its quickstart copies. No application behavior depends on those values. Those defensive collector rules can remain; they are not a substitute for preventing collection in the application.

The installed, lock-resolved `@opentelemetry/instrumentation-graphql` version is **0.35.2**. Its `build/src/instrumentation.js` adds input variables only when `allowValues` is true. Its `build/src/utils.js` masks string, block-string, integer and floating-point tokens when false, but retains comment tokens and GraphQL name/enum tokens in `graphql.source`. Merely setting `allowValues: false` therefore does not make query-body export safe. This patch sets it false and removes `graphql.source` in `SpanProcessorWrapper.onEnd`, immediately before calling the exporting parent processor. The same boundary covers parse, execute and resolver spans. Operation/type/timing metadata is retained; raw or partially masked query documents are not exported by this processor.

Tests invoke the exact installed GraphQL plugin's execute-span path with nested variables, string/block-string/numeric literals, comments and enum literals, then exercise the export boundary. They prove that variables are omitted, scalar values are masked by the configured plugin, and source text (including the comment/enum tokens it leaves behind) is absent from the exported attributes. Wrapper tests cover realistic positional and object credential inputs, property access/enumeration traps, grouped wrappers, explicit safe metadata, call results and error behavior.

## Remaining telemetry sinks

This is a correction to automatic argument and GraphQL source capture, **not a claim that all telemetry is sanitized**. A separate audit must consider:

- Explicit `spanAttributes`, `addAttributesToCurrentSpan`, events and direct span setters remain caller-controlled. Existing call sites deliberately include account/user identifiers and operational details. Sensitive values supplied explicitly are not scrubbed by this patch.
- `addAttributesToCurrentSpanAndPropagate` accepts caller-provided entries, and `SpanProcessorWrapper.onStart` copies all active baggage values into span attributes. The configured global propagator is W3C trace context, rather than a baggage propagator, but application-created baggage is still a sink. No new inbound baggage extraction is enabled here.
- Error handling still records exception messages/stacks. `recordGqlErrors` serializes GraphQL errors and their original messages; the plugin records parser/validation errors. Such errors can quote invalid inputs, unexpected names or backend details. Removing `graphql.source` does not remove text embedded in an error.
- GraphQL operation names, aliases, field paths and schema metadata remain trace metadata. Client-selected names can themselves contain sensitive text. This patch does not implement a registered-operation allowlist or an operation-name policy.
- HTTP instrumentation captures URL/target data, including query strings in the installed adapter. The configured incoming header allowlist includes client name/version, IP and user agent; it does not include Authorization, cookies or Appcheck. Credentials or signed capabilities placed in URLs remain a separate risk.
- The installed MongoDB default serializer replaces top-level command values with `?` while enhanced reporting is off. It still emits database/collection/operation metadata and command keys. No enhanced query-value reporting is enabled by this patch.
- The installed Redis serializer records command-dependent arguments. For example, its default implementation retains all arguments for EVAL and many lookup commands, and retains keys for SET. Keys, scripts or arguments can contain identifiers, credentials or personal data. This patch does not alter that serializer.
- gRPC/network instrumentation, custom exporters/processors, logging and external provider SDK diagnostics need their own review. This patch adds no logger, exporter or provider request. It cannot erase previously collected spans or change collector retention/access controls.

The Bridge owned-KYC fix and initial device-account work should integrate this change before release. Historical collection requires a separate access/retention review; neither code changes nor mocked tests establish that old telemetry has been deleted.

Validation: 23 focused tests pass across the new privacy suite and existing tracing suite. All three TypeScript configurations (`tsconfig.json`, `tsconfig.d.json`, `tsconfig.no-implicit-any.json`), touched-file ESLint, and `git diff --check` pass using Node 24 and the frozen-lock dependency installation. No `.env` file was loaded.
